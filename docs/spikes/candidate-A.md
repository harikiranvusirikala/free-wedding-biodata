# PDF spike, candidate A: `@react-pdf/renderer` 4.9.0

> **After the decision (2026-11-21, [PDF_SPIKE.md](PDF_SPIKE.md)):** only a curated set of the files named below is kept in `pdf/`; the rest are regenerated by `npm run test:e2e` into `test-results/spike/`. Candidate A's code (`src/pdf-spike/react-pdf/`, `scripts/spike-react-pdf.mts`) and `@react-pdf/renderer` were removed, as the plan says for engines not chosen.

Step 0.2, candidate A. The fixture (`test/fixtures/scripts.ts`, `ALL_PAGES`) drawn as a minimal Classic Gold equivalent with react-pdf and the same Noto TTFs as `public/fonts/`, rendered in Node, rasterised with macOS PDFKit and checked by eye, by text extraction and by comparing glyph IDs with HarfBuzz.

**Verdict: reject.** Out of the box, react-pdf throws on Telugu, Malayalam and Punjabi, so no PDF is made at all. It draws Bengali wrongly, and it silently drops characters at the end of some Hindi, Marathi and Bengali strings. Hindi, Tamil, Kannada, Marathi and Gujarati glyphs are correct. Copy and paste of Indic text is wrong in every language. On top of that it brings a second layout engine (Yoga + textkit), which goes against VISION D1 (one layout for preview, print and PDF).

## The crash (te, ml, pa)

Stock fontkit 2.0.4 (react-pdf's shaper) throws `TypeError: Cannot read properties of null (reading 'xCoordinate')` in `GPOSProcessor.getAnchor`. The cause: a MarkBase/MarkLig record whose anchor for the mark's class is NULL. That is valid OpenType, and HarfBuzz simply skips the attachment. `renderToBuffer` rejects, so the whole document fails, not just one word. Triggers in the fixture:

- **Telugu:** every C + ్ + ర (ra-vattu): శ్రీ, ప్రదేశం, తండ్రి, శ్రీమతి, క్రికెట్ (8 words).
- **Malayalam:** 12 words, for example പേര്, ലക്ഷ്മി, ഓഗസ്റ്റ്, ടെക്.
- **Punjabi:** nearly any consonant + vowel sign (ਕੇ alone crashes; 23 of 60 words).

A three-line in-memory patch makes all three render: skip `applyAnchor` when either anchor is NULL. Production would need `patch-package` on a transitive dependency. The `-patched` files below are only there to show what the rest of the pipeline does once the crash is out of the way.

**Why characters disappear.** fontkit's glyph IDs for hi and mr match HarfBuzz exactly, yet characters are missing from the PDF, so the loss happens later, in react-pdf's textkit. `slice` and `glyphIndexAt` in `@react-pdf/textkit` cut runs by string index with a binary search over `glyphIndices`, and re-shape partly covered glyphs on their own (`font.layout` on a fragment). Both assume the glyph order follows the character order. Indic shaping breaks that: pre-base vowel signs move left and reph moves right. The result is that glyphs at the end of a run get dropped, or rebuilt without their context. This explanation is inferred from the code plus the symptoms; I didn't trace it step by step. The patch doesn't touch this, so even fully patched, hi, mr and bn stay wrong.

## Text extraction (copy and paste)

react-pdf writes no `ActualText`, and its ToUnicode maps follow glyph order, so PDFKit's `page.string` gives visual order:

- the pre-base vowel comes before the consonant: `िक` for कि, `ेपशा` for পেশা, `ெபயர்` for பெயர்;
- reph comes after the cluster: `शमार्` for शर्मा, `कनार्टक` for ಕರ್ನಾಟಕ;
- Telugu, Kannada and Malayalam conjuncts come out reordered: `శీ్ర` for శ్రీ, `്രശീ` for ശ്രീ.

Fixture strings found verbatim in the extracted text:

- **English:** 43/43 strings (all 788 words).
- **Indic (out of 23 strings):** te 9, hi 12, ta 10, kn 10, ml 11, mr 14, gu 13, bn 6, pa 11. Only strings with no reordered cluster survive.

Search and copy and paste of Indic names and places therefore fail.

## About text flowing to page 2

The ~600-word About (4 paragraphs) starts under the About bar on page 1 and continues on page 2. The split falls at a line boundary in the middle of a paragraph. The `fixed` gold border repeats on page 2, nothing overflows, and the photo box and the sections stay on page 1 (`wrap={false}` per section, `minPresenceAhead` on the About bar).

One react-pdf gotcha I hit: a unitless `lineHeight` multiplies the element's *own* `fontSize`, and falls back to 18 pt if that isn't set, rather than the inherited size. The first render had double line spacing because of this. The fix is to repeat `fontSize` on the paragraph style.

## Node notes

- tsx loads `.tsx` files as CommonJS here, because the project has no `"type": "module"`. That turns react-pdf's ESM imports into `require()`, which fails on `@react-pdf/hyphenate/en-us`: its export map is import-only, giving `ERR_PACKAGE_PATH_NOT_EXPORTED`. A one-line `package.json` with `"type": "module"` in `src/pdf-spike/react-pdf/` fixes it. `--conditions=import` doesn't work: tslib then breaks.
- It works with React 19.3.1. The Next build and browser use were not exercised.

## Against the decision rule (BUILD_PLAN Step 0.2)

1. **Matches Chrome in all ten languages:** fails. te, ml and pa crash; bn is garbled; hi, mr and bn lose text; kn draws ಕ್ಷಿ in a different form.
2. **One-click download and Share, plus a page image:** not tested. A page image would need a separate canvas renderer.
3. **One layout for preview and export:** fails by design. react-pdf lays the document out again with Yoga and textkit, separately from the HTML preview.
4. **Selectable text:** yes, but Indic copy and paste is wrong.
5. **Least code and dependency surface:** about 440 KB gzip, and a patched transitive dependency (fontkit) would still not fix textkit.
