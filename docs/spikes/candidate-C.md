# PDF spike, candidate C: vector PDF writer driven by the browser's layout

> **After the decision (2026-11-21, [PDF_SPIKE.md](PDF_SPIKE.md)):** only a curated set of the files named below is kept in `pdf/`; the rest are regenerated by `npm run test:e2e` into `test-results/spike/`.

Candidate C takes Chrome's own layout (the display list read from the reference page, `docs/spikes/pdf/display-list.json`: every visual line of text with its baseline, x and width, plus rects, the photo and the SVG ornaments), shapes each line with **HarfBuzz** (`harfbuzzjs` 1.6.4) using the same Noto TTF, and writes the glyph IDs with **pdf-lib** 1.17.1's low-level objects. Line breaks, wrapping and positions are Chrome's. The shaping is HarfBuzz's, which is the same shaper Chrome uses.

Measured in Node 26 on an Apple M1 Pro. PDFs were rasterised with macOS PDFKit at 1588 px wide (2× of 96 dpi, the size of the reference screenshots).

## Files

- `src/pdf-spike/vector/`: the engine (no Node or DOM APIs, so the same code runs in the browser and in Node).
  - `write-pdf.ts`: `writePdf(list, fonts, options) → Promise<Uint8Array>`.
  - `shape.ts`: runs split by font fallback and script, then HarfBuzz shaping, letter spacing and the ToUnicode guesses.
  - `subset.ts`: wraps `harfbuzz-subset.wasm` (retain-gids).
  - `svg-to-pdf.ts`, `svg-path.ts`, `matrix.ts`, `xml.ts`, `color.ts`: SVG → PDF operators.
  - Tests: 29 Vitest tests in 5 files, jsdom environment.
- `scripts/spike-vector.mts`: writes `docs/spikes/pdf/C-all.pdf` and `C-<lang>.pdf`, and prints timings, sizes and width agreement.
- `docs/spikes/pdf/C-<lang>-p1.png`, `C-en-p1.png`, `C-en-p2.png`: PDFKit renders of `C-all.pdf`.
- `docs/spikes/pdf/compare-C-<lang>.png`: Chrome's screenshot on the left, C on the right. Each shows the title, both detail sections and the first paragraph lines.
- Evaluation tools, outside the repo: `/tmp/spike-pdfkit-c/render.swift` (PDFKit renderer and text dump), plus `compare.mts`, `offsets.mts`, `actualtext.mts` and `extract-score.mts`.

## How it works

- **Pages:** A4, 595.28 × 841.89 pt. One `0.75 0 0 -0.75 0 841.89 cm` at the top of each page lets everything below work in CSS px, with y pointing down.
- **Text:** each run is split into graphemes (`Intl.Segmenter`). Each grapheme goes to the first family in `[run family, "Noto Sans"]` that has all its code points. Pieces are then split by script, with Common and Inherited characters joining their neighbours. Each piece is shaped with the full line as context, with the script set and the language taken from the page `lang`, so Marathi gets its own Devanagari forms.
  - Letter spacing is added after every HarfBuzz cluster.
  - Glyphs are drawn with `Tm` once per run, then `TJ` arrays. Position differences go in as TJ adjustments, and `Ts` handles vertical mark offsets.
  - Each run is wrapped in `/Span << /ActualText <FEFF…> >> BDC … EMC`.
- **Fonts:** one Type0 / CIDFontType2 font per family and weight, with Identity-H encoding and `CIDToGIDMap /Identity`. The font is embedded once and subset by `harfbuzz-subset.wasm` to the glyphs used anywhere in the document.
  - Retain-gids keeps the shaped glyph IDs valid.
  - GSUB, GPOS, GDEF and hinting are dropped, because a PDF needs only outlines.
  - `/W` comes from HarfBuzz advances. A best-effort ToUnicode CMap is included.
- **Justified text:** the display list does not record `text-align`. A line that has spaces, is at least 40 % of the page wide, is exactly as wide as the widest line starting at the same x, and that HarfBuzz finds narrower than Chrome's box, gets the difference spread over its spaces (as Chrome does). This applied to 38 lines: every full line of the justified paragraphs, and nothing else.
- **Rects:** filled or stroked with their radius; CSS borders are stroked inset by half their width. **Images:** each distinct data URL is embedded once (JPEG via `embedJpg`, PNG via `embedPng`) and clipped to the radius.
- **SVG:** a small XML reader feeds a converter that handles:
  - `path` (all commands, absolute and relative; arcs become cubics), `circle`, `ellipse`, `rect`, `line`, `polyline`, `polygon` and nested `g`.
  - `transform` (matrix, translate, scale, rotate, skew) and inherited presentation attributes, also when set through `style`.
  - fill, stroke, width, cap, join, miter, dash, fill-rule and opacities.
  - `linearGradient` fills and strokes as **real PDF axial shadings**: a shading pattern whose matrix maps the gradient's bounding-box space through the element's transform. More than two stops become a stitched type 3 function.

  Each distinct SVG becomes one Form XObject, drawn by reference on every page that has it.

## Width agreement (HarfBuzz vs Chrome)

Out of 437 runs, 0 differ by more than 1.5 %.

- **399 runs that are not justified:** median 0.01 %, p95 0.56 %, max 0.71 %. In absolute terms: median 0.010 px, p95 0.023 px, max 0.028 px. All 98 runs over 0.3 % are the 4 px-wide ":" runs. These residuals fit Chrome's 1/64 px LayoutUnit rounding of the measured box.
- **Letter-spaced runs** (titles at 2.08 px, headings at 0.3 px) in all ten scripts: within 0.02 %. HarfBuzz clusters receive spacing exactly as Chrome does.
- **38 full justified lines:** HarfBuzz's natural width was 0.11 %–10.52 % narrower (Tamil −10.5 %, because long words leave few spaces). After spreading the gap over the spaces, they land exactly on Chrome's width.
- **Fallback font:** no run needed one. Every Noto script font here also contains Latin, digits, "–" and the dandas. Fallback is implemented and unit-tested anyway.

## Text extraction (copy and paste)

- **ActualText:** all 437 spans in `C-all.pdf` decode to exactly the original run text (`actualtext.mts` reads the content streams back). Acrobat honours `/ActualText`; as far as I know Chrome's PDFium and pdf.js do too. I could not run any of them in this sandbox, so this is **not verified here**.
- **Apple PDFKit** (Preview, iOS Files and Safari) ignores ActualText. I tried the span both outside and inside `BT…ET`. PDFKit therefore uses the ToUnicode CMap.
  - The CMap maps nominal glyphs to their code point, single-glyph clusters to the whole cluster, and leftovers in a cluster to its first other glyph. When a glyph appears in several places, the most confident mapping wins.
  - **Result:** English and Telugu come out almost right ("శ్రీ వెంకట కృష్ణమూర్తి మండపాటి" extracts exactly). Pre-base vowel signs come out in visual order: Devanagari "िक" for कि, Tamil/Malayalam "ெப" for பெ, Bengali "িক". Some conjunct-internal glyphs are wrong or missing.
  - Runs found verbatim in PDFKit's page text, C (and B, Chrome's own PDF):

    | Page | C | B |

    | en p1 | 72/72 | 67 |
    | en p2 | 38/38 | 30 |

    These counts include trivial runs such as ":". In PDFKit, Chrome's own PDF loses whole lines after the first complex cluster. C is better than B in PDFKit, but neither is exact for Indic text there. A glyph→Unicode map cannot express reordering.
  - PDFKit joins separate runs that sit close on one line without a space ("Page3 of 11", "Name:"), because the display list has separate runs and no space glyphs between them. Including a trailing space in the ActualText, or drawing a real space glyph, would fix this for viewers that honour it.

## Lazy-load cost in the browser

Minified with esbuild and compressed with `gzip -9 -c | wc -c`:

| Part | Raw | Gzip |
|---|---|---|
| Candidate C's own code | 26 KB | 11.5 KB |
| pdf-lib with pako, @pdf-lib/standard-fonts (130 KB raw, not tree-shaken) and upng | 432 KB | ~179 KB |
| harfbuzzjs JS glue | 43 KB | 12.1 KB |
| harfbuzz.wasm | 444 KB | 179 KB |
| harfbuzz-subset.wasm | 684 KB | 275 KB |
| **Total, loaded on the first download** | **≈ 1.63 MB** | **≈ 656 KB** |

The fonts come on top: 3.5 MB for all 18 TTFs. In practice only the document's two or three fonts are needed, and the preview has already loaded them from the same URLs.

The cost could be cut a lot:

- A small TrueType glyf/loca subsetter (zero unused glyphs, keep composite components, about 150 lines) could replace `harfbuzz-subset.wasm` and save 275 KB gzip.
- The writer uses pdf-lib only to serialise objects and embed JPEGs. A minimal PDF serialiser (about 300 lines) would save about 179 KB gzip.
- Together these would bring the download to about 200 KB gzip.

## SVG and gradients

The corner foliage, the borders and the motif all render as vectors, matching Chrome:

- 142 gradient-filled leaves with `rotate(…) translate(…)`, gradient strokes, and mirrored corners through `scale(-1 1)`.
- The three-stop `linearGradient` is a true axial shading over each element's bounding box, and the per-leaf light-to-dark direction matches (see `C-en-p1.png` against `reference-en-p1.png`).
- One SVG rule is implemented: an `objectBoundingBox` gradient on an element with zero width or height isn't drawn.
- Not supported, and reported through `onWarning` rather than drawn: `radialGradient`, `text`, `use`, `clipPath`, `mask`, `filter` and `pattern`. Group `opacity` is applied per shape.

## Limitations and open points

- **The display list should carry more:**
  - `text-align` (or per-word x positions), so justification isn't inferred.
  - The exact baseline. It is currently computed from canvas ascent, and lines ending in .25 sit ½–1 CSS px lower than Chrome's screen render.
  - Spaces between separate runs on one line, for extraction.
  - Font style (italic).
  - The photo's `object-fit` and crop. The fixture's photo already matches its box.
- **Copy and paste is exact only where `/ActualText` is honoured.** Apple's PDFKit gets the best-effort ToUnicode map, with pre-base vowel signs in visual order.
- **Browser loading is not exercised in this spike.**
  - `harfbuzzjs` loads `harfbuzz.wasm` through `new URL(…, import.meta.url)`, and its Node branch has an `import("module")`. Whether Turbopack bundles both cleanly needs a real build.
  - The caller must pass `subsetWasm` (bytes or a loader such as `() => fetch(url).then((r) => r.arrayBuffer())`).
- **Fixture scope:** only the content in this fixture was checked. Untested: no RTL, no vertical text, no colour fonts, no fallback beyond Noto Sans, and no emoji.
- **Fixture gaps:** the fixture has no PNG image, no stroked or rounded rect and no transparent colour, so those paths are written but not checked against Chrome.

## Against the decision rule (BUILD_PLAN Step 0.2)

1. **Glyph-for-glyph in all ten languages:** yes. No glyph difference found, positions within 1 CSS px, and widths within 0.03 px of Chrome on every run that isn't justified.
2. **One-click download and Share, plus a page image:** in principle, yes. A `Uint8Array` is produced in the page and needs no print dialog. The same display list can drive the canvas image (D38). The phone checks belong to the owner.
3. **One layout for preview and export:** yes. Chrome lays out once, and the writer only draws.
4. **Selectable text:** yes. ActualText is exact. In PDFKit, extraction is best-effort but better than Chrome's own PDF there.
5. **Least code:** about 1,700 lines of our own code, comments included. The dependency weight (≈ 656 KB gzip, lazy) is the main cost, and it can be reduced as described above.

**Verdict:** candidate C meets the quality bar. Its output is indistinguishable from Chrome's layout in all ten scripts, the files are small (24–41 KB per language document, 177 KB for all 11 pages), and it takes milliseconds. The remaining work before it can ship is engineering, not risk: record alignment and baselines in the display list, cut the lazy bundle, and confirm wasm loading in a Turbopack build and on real phones.
